# UCache release notes

What each version brings, newest first. The DLLs of every version are on the [releases page](https://github.com/pkoutsogiannis/ucache/releases).

## 1.0.0.2

Lookups stay fast as the cache fills, processes that IIS kills or starts at any moment no longer break the cache, `ucache_clear()` no longer holds up the pool and full caches hold it up for much less time, stored arrays take much less memory, and the settings and pool names are read as written.

- **More hash buckets:** the hash table of the cache has one bucket per 512 bytes of `ucache.size` (16381 for the default 8 MB, 1048573 for 512 MB), instead of one per 32 to 64 KB in 1.0.0.1 (197 for 8 MB, 12853 for 512 MB). Its chains hold 2 to 3 entries on average even in a cache full of the smallest entries, where they could hold hundreds. With 500,000 entries of 40-character keys in 128 MB, `ucache_get()` takes about 1 microsecond, found or not, instead of 9.4 for a key found and 18.3 for a missing one; with 500,000 entries of integers, short strings and serialized rows in 512 MB, 1.15 instead of 3.41 for a key found and 1.00 instead of 5.92 for a missing one (PHP 7.2).
- **Long keys:** keys longer than 260 characters are hashed in full. 1.0.0.1 put all of them in the same bucket, so every such key stored slowed down the lookups of the others: with 5,000 keys of 300 characters, `ucache_get()` takes 1.4 microseconds instead of 11.1 for a key found, and 1.2 instead of 21.9 for a missing one (PHP 7.2).
- **A process killed in the middle of an update:** a process that ends while it holds the cache lock or the allocator's lock (an IIS FastCGI activityTimeout or requestTimeout, a stopped or recycled pool, a crash, or memory_limit on PHP builds that end the process there) no longer leaves the shared memory corrupt for every process of the pool. Each update of a hash chain and the count of entries, of a `ucache_clear()`, of the lists of free blocks, the block headers and the counts of the allocator now first saves what it changes in a log in the shared memory, and the next process to take the lock puts it back, so that the update did not happen: an entry being removed stays, an entry being added is left out (its memory is lost), a clear does not clear, a block being allocated stays free, and a block being freed stays in use, lost with the rest of its entry. In 1.0.0.1 the processes went on with the half-done update: depending on where the process ended, the next process crashed, every later `ucache_set()` failed and every read missed, a hash chain listed one entry twice and led to freed memory, or the counts of entries and blocks drifted.
- **total_abandoned_lock_count:** `ucache_info()` has a new key, `total_abandoned_lock_count`: the times since the cache was created that a process found the cache lock or the allocator's lock abandoned (the process that held it ended without releasing it), and ucache.php shows it on its Scavenged entries tile. On the CVE-patched PHP 7.2, which ends the process at memory_limit, a `ucache_get()` that reaches memory_limit while it copies a value out is one of them (nothing is undone then: a copy out changes nothing).
- **Starting while the cache is created or closed:** a process that started while the last process of its pool was closing the cache, or after a process died while it created the cache or the pool's table of caches, could crash on its first call with a key (a division by zero, exit code 0xC0000094), and so could every process that opened the cache while it ran; or it initialized the memory allocator again under the entries of the cache, after which entries were lost or calls crashed (0xC0000005); or it ran without a cache, every function returning false, as did every process of the pool that started while it ran. Whether the shared memory must be initialized is now decided once, under the init mutex of the cache (of the table, for the table), from whether the memory already existed and from a mark that the process that initializes it writes last, so such a process gets a working cache, and one that starts while the last process is closing the cache keeps its entries instead of starting a new cache. One named mutex fewer is created per cache (`..._ALLOC_INIT`).
- **ucache.size while the last old process ends:** a process that started while the last process with another `ucache.size` was closing the cache could crash (a larger size) or initialize the allocator again under the entries without a word (a smaller size); it now uses that cache at the size it has, as the processes that start while the cache is in use already did. After changing `ucache.size`, stop the pool and start it again once its php-cgi processes have exited.
- **ucache.filemapdir after a killed process:** a process that maps the file that a killed process left behind now initializes it as a new cache; 1.0.0.1 reopened the entries of that dead cache, which could be half written, when another process still had the init mutex of the cache open (otherwise it deleted the file).
- **A process killed while it records the cache:** a process killed while it added the cache to the pool's table of caches could leave an entry without a name or size there, and every process of the pool that started while the table was in use then ran without a cache; an entry is now published only once it is complete, and one found without a name or size is written again.
- **ucache_clear() no longer holds up the pool:** the cache is now emptied at once for every process, under the cache lock, and its entries are then freed in batches with the lock released between them, so the other processes go on reading and writing: with a full cache of 512 MB (2.5 million entries of about 200 bytes, PHP 7.2), a read in another process waited at most 0.6 ms during the clear, where it waited the whole clear (about 4 to 4.5 s) in 1.0.0.1, and a write about 0.1 s at most: it first helps free the entries for up to that long, so that few values go in the holes of the entries being freed, where they would keep the free memory in small pieces (with 4 processes writing during the clear of a full 512 MB cache, a read waited about 4 ms at most, and the clear left about 70 free blocks, in which a value of 8 MB fitted); a write that needs more memory than the freed entries have yet joined into fails after about 0.12 s (7 of 27 writes of 1000 bytes made during such a clear did); the clear itself took 1.5 to 2.1 s instead of about 4 to 4.5 s. A `ucache_clear()` while another process is still freeing the entries of an earlier one now returns at once (under 0.1 ms), where 1.0.0.1 waited for the lock until the earlier clear had ended and then went through the table again, and a process killed during a clear (an IIS FastCGI timeout) now leaves the cache cleared, where 1.0.0.1 left the entries it had not reached readable; what it had not freed is freed by writes, the ends of requests (while `ucache.gc.interval` > 0), lookups, steps or the next `ucache_clear()`.
- **Stored arrays take the memory they hold:** before copying an array, `ucache_set()` and `ucache_add()` now count what its tables and strings take, each part once however often it occurs, and put them in one block of that size, instead of in chunks of 512 bytes to 4 KB that small tables left mostly empty: a row of 14 short strings takes 2,080 bytes instead of 6,400, an array of 8 short strings 1,272 instead of 5,768, and 500,000 entries in 512 MB, 6% of them rows of 14 strings (about 1.6 KB serialized) stored as arrays and the rest integers and short strings, took 185.8 MB instead of 255.4 (PHP 7.2). Storing an array is faster too (a row of 14 short strings: 6.6 microseconds instead of 17.5), several processes that store arrays at once take turns on the allocator's lock for fewer allocations, and deleting, replacing or clearing an array frees a few blocks (an array of 100,000 small arrays: in under 0.1 ms). Reading is as fast as before.
- **A fragmented cache stays fast:** free blocks are now kept in lists by size, so storing a value takes the same time however many free blocks the cache holds (unless many of them are in its list and a little too small for it, while the lists of larger sizes are empty): with 250,000 free blocks too small for it, a `ucache_set()` of a 1000-byte string takes about 4 microseconds, where 1.0.0.1 went along a single list of all the free blocks, in address order, to the first one large enough. A block is no longer split when the rest could not hold even the smallest block the cache asks for (16 bytes): 1.0.0.1 left free blocks of 8 bytes that nothing could use.
- **A full cache with ucache.gc.evict:** a value larger than the free memory, in a cache with at least `ucache.gc.evict` percent free and nothing expired, now makes the full pass evict and is stored, where 1.0.0.1 evicted nothing, failed the write and made every process skip the full pass for a second or more. A value that takes, counted before it is copied, more than the empty cache holds (8,253,952 bytes for 8 MB) now fails at once, before it takes any shared memory: no full pass runs and nothing is removed or evicted, where 1.0.0.1 first evicted every entry, and the writes of the other processes no longer run out of memory and evict entries because of it. A big value that fits is stored in fewer rounds.
- **Full passes are faster:** with the larger hash table, the full pass of a full cache goes through the entries faster, and it now frees what it removes 32 entries at a time, with one hold of the allocator's lock each, and reads the free memory every 64 evictions or so instead of after each one: in a full 512 MB cache of 2.6 to 2.7 million entries of 200 bytes, a pass that frees nothing (`ucache.gc.evict=0`) takes about 90 to 110 ms instead of 330, and an eviction pass (`ucache.gc.evict=10`) about 0.5 s instead of 1.6 s; filling such a cache with 3.2 million entries with `ucache.gc.evict=10` took about 13 s instead of about 3 minutes (PHP 7.2). After a mass expiry, a pass held the cache lock 0.24 to 0.26 s for 635,000 entries in 128 MB.
- **`ucache.gc.step`:** a fixed value goes through the larger table more slowly: with 500,000 entries in 512 MB, steps of 1000 buckets every 10 seconds now cover their 1000 buckets and go through the table in about 2.9 hours, where 1.0.0.1's stopped at their 1 ms limit after about 32 of its 12,853 buckets and went through it in about 67 minutes. A larger value gives a shorter sweep, and the automatic size, 0, grows with the table. A step reads the clock every 256 buckets instead of every 16, as most buckets are empty now, and also after each bucket in which it removed entries, so that a step that removes many entries stops after about 1 to 2 ms.
- **Scavenger steps on writes:** with `ucache.gc.threshold`, a write now runs a step only once a second has passed since the last step in any process of the pool, a tenth of a second after a step that removed entries, or a hundredth after one that removed entries while at most a quarter of the threshold was free, instead of on every write, and the other writes no longer take the allocator's lock to look at the free memory: with free memory at or below the threshold (`ucache.gc.threshold=100`, steps of 1000 buckets, 512 MB), one process made 2.32 million writes in 3 seconds instead of 0.12 million (with `ucache.gc.threshold=0`, 2.05 million instead of 1.29 million; PHP 7.2). After a mass expiry, the steps on writes no longer remove the expired entries at the cost of every write: they remove some thousands of entries a second for about 1% of the cache lock (500,000 expired entries in 128 MB, threshold 50: back above the threshold after about 40 seconds), and if the cache fills first, the full pass of a full cache removes the rest at once (about 0.25 s of cache lock for 635,000 expired entries). With `ucache.gc.interval=0` the automatic step goes through buckets / 300 hash buckets instead of 16, and a negative `ucache.gc.threshold` acts as 0 instead of 100.
- **Times past 49.7 days:** expiry by ttl, `ucache.gc.ttl`, `ucache.gc.interval`, the back-off of the full pass of a full cache, and the uptime and ages that `ucache_info()` reports now use the 64-bit tick count of Windows, which does not wrap. So a ttl of 4294967 seconds (about 49.7 days) or more now expires (1.0.0.1 never expired it), an expired entry that nothing has removed no longer becomes readable again for its ttl every 49.7 days, a `ucache.gc.ttl` or `ucache.gc.interval` of about 49.7 days or more now takes effect (1.0.0.1 never removed such an entry or ran such a step), the processes no longer skip the full pass of a full cache for up to a minute every 49.7 days after one that freed nothing, and `total_cache_uptime`, `age_seconds` and `last_scavenge_seconds` no longer start again from 0 every 49.7 days.
- **Failed reads (PHP 8.1 to 8.5):** a `ucache_get()` that fails, because the value is nested too deeply for the C stack left in a Fiber, or because it reaches memory_limit on a runtime with delayed out-of-memory handling (8.2.35, 8.3.36, 8.4.27, 8.5.12 and later builds), now frees what it had copied after releasing the cache lock. 1.0.0.1 freed it under the lock, where PHP's garbage collector could start: unrelated destructors then ran while every other process of the pool waited for them, and a value that refers to itself could crash the process when PHP's GC root buffer was nearly full. In a Fiber, those destructors also ran on the exhausted stack of the copy: PHP 8.3 refused each of them with an Error, which came out of `ucache_get()` instead of false, and on 8.1 and 8.2 one that needed more stack crashed the process. `ucache_get()` still returns false, sets `$success` to false and leaves the entry in place.
- **`$GLOBALS` on PHP 7.2 to 8.0:** from a script whose top-level code uses no variable, `ucache_set()` and `ucache_add()` now store `$GLOBALS` (as the value, nested in an array, or behind a reference) as it was when they were called. 1.0.0.1 copied it after serializing its objects, so globals that `__sleep()` or `__serialize()` added or changed were stored, and a `__sleep()` that added an object or bound an unset global (`global $x;`) made the call return false without a warning. `ucache_get()` and `ucache_delete()` given a key array that is the symbol table itself (before PHP 8.1, a copy of `$GLOBALS` kept in a variable is that table) now walk a copy of it, as `ucache_set()` and `ucache_add()` already did: `ucache_get()` no longer reads freed memory when a `__wakeup()` adds globals, and both read the variables of the top level as their values instead of warning that key array elements can only be string or long.
- **`array_values($GLOBALS)` on PHP 7.2 to 8.0:** `ucache_set()` and `ucache_add()` of a list of the entries of `$GLOBALS` (`array_values($GLOBALS)`, `array_chunk($GLOBALS, 10)` without its keys, or a value that holds one) now return false without a warning; 1.0.0.1 copied it again and again until memory_limit ended the process (with no memory_limit, a stack overflow did). Arrays that `array_merge()`, `array_slice()`, `array_reverse()` or `array_chunk()` with its keys make of `$GLOBALS` are stored as before, with the values of the variables.
- **ucache.size:** the setting takes a number of megabytes, or a size with a `K`, `M` or `G` suffix in any case, which a `B` may follow (`64`, `64M`, `64MB`, `64 MB`, `1G`, `65536K`; `K` is rounded up to whole megabytes), always in decimal: `064` is 64 MB, where 1.0.0.1 read it as octal (52 MB). If php.ini wrote the size with a suffix such as `64M`, the cache now has that size, where 1.0.0.1 made it 930 MB without a word: check that it is large enough. A size outside 5 to 930 MB is clamped, digits followed by other text (`64MiB`) are taken as megabytes, and any other value (`abc`, `-1`; also `0x40`, which 1.0.0.1 read as 64 MB) gives the default 8 MB, each with a startup warning; an empty value gives 8 MB without one (1.0.0.1 gave 5 MB). `ini_get()` and `phpinfo()` show the value as written; ucache.php shows the size of the cache under it.
- **A cache that cannot be created:** when PHP starts, a cache that cannot be created (the file in `ucache.filemapdir` cannot be created, shared objects of another account, an initialization lock that another process kept for 30 seconds, the commit limit) now raises a startup warning that names the likely cause and the Windows error, and `phpinfo()` shows `User cache => unavailable` instead of `enabled`; 1.0.0.1 said nothing. PHP writes startup warnings to its error log and to the Windows Application event log (source `PHP-<version>`, event ID 4: always on PHP 7, on PHP 8 with `log_errors` on or `display_startup_errors` off). Every php-cgi process logs the warning again when it starts: fix the setting rather than ignore it. Under the CLI without `ucache.enablecli`, where no cache is created, neither these warnings nor the `ucache.size` ones are raised.
- **Which processes share a cache:** the application pool id (`ucache.apppoolid`, else `APP_POOL_ID`) now goes into the names of the cache's shared memory and locks as a 64-bit hash, so different application pools no longer share a cache by accident: 1.0.0.1 reduced the id to one of 899,999 numbers, and `site907` and `site1499`, for example, shared one. `APP_POOL_ID` is read as Unicode, and `ucache.apppoolid` as UTF-8 when it is valid UTF-8, otherwise in the ANSI code page, so the setting and the environment variable give the same cache for any name; 1.0.0.1 read `APP_POOL_ID` in the ANSI code page, where pool names that differ only in other characters were the same.
- **Empty settings:** an empty `ucache.apppoolid` (also `none`, `off`, `no`, `false` or `null`), `ucache.filemapdir` or `ucache.namesalt` now counts as not set. 1.0.0.1 put every process with an empty `ucache.apppoolid` in one cache, whatever `APP_POOL_ID` or its parent process (anyone who used that to share one cache between unrelated processes must now give them a name), put the file of an empty `ucache.filemapdir` in the root of the current drive (or had no cache where the pool's account could not write there), and kept the processes with an empty salt apart from the others.
- **ucache.filemapdir:** only the cache of an application pool is backed by a file in the folder (and, as before, only when the pool id names an IIS application pool, whose account gets access to the file); the caches of processes grouped by their parent process stay in the paging file, where 1.0.0.1 backed with a file those whose parent process id was above 99999. A folder in which the file cannot be created still leaves the pool without a cache, now with a startup warning that names the folder.
- **ucache.php, Clear All:** the token of the button is now made from `PASSWORD`, the random value of its cookie and the path of the page, where 1.0.0.1 used the value of the cookie itself, so another host of the same site, which can set that cookie, can no longer make a logged-in browser clear the cache, and a copy of the page in another file does not accept the tokens of this one. A page loaded before the upgrade must be reloaded before its Clear All works.
- **ucache.php, origin checks:** the page also refuses to clear the cache when the browser says, in its `Sec-Fetch-Site` or `Origin` header, that the form comes from another origin (behind a reverse proxy, the proxy must pass on the `Host` header), and it sends `Cache-Control: no-store`, so that neither the browser nor a proxy keeps a copy of it.
- **ucache.php with IIS authentication:** Clear All now needs `PASSWORD` changed from the default `ucache` (or from an empty one), because nobody types it there and it is the only secret behind the button; until then the page shows a note in its place. Make `PASSWORD` a long random value, and change `USERNAME` too: requests that reach the page without IIS authentication can still log in with the two.
- **ucache.php, `USE_AUTHENTICATION`:** any value other than 0 now turns authentication on; with a value such as 2, 1.0.0.1 asked for no authentication and still offered Clear All.
- **ucache.php, other fixes:** the page no longer says that the user cache is not available, or that FastCGI impersonation is disabled, when the setting is on but written as a number other than 1 or as a quoted `On` (or, for `ucache.enabled`, set to `on` with `ini_set()`); Clear All no longer redirects to a broken address when the path of the page holds `&` or characters outside ASCII; when the cache could not be created, the page points to the startup warning in the PHP error log or the Windows Application event log; and on PHP 8.5, a `start` parameter too large for an integer (in the address of a page of entries) no longer raises a warning, which with `display_errors` on came out before the page and dropped its headers (the cookie of Clear All and the refusal to be shown in a frame).
- **The cost:** the hash table takes 8 bytes per 512 bytes of the cache, about 1.6% (8 MB of a 512 MB cache, where 1.0.0.1's took 100 KB), and the lists of free blocks by size, the undo logs and the new fields of the cache's header 3,320 bytes: `memory_free` of an empty 512 MB cache is 528,478,720 bytes instead of 536,767,800, and a full 512 MB cache holds 2,645,924 entries of 200 bytes instead of 2,687,425. Entries of integers and strings take as much memory as before.
- **No paths of the build machine in the DLLs:** `php_ucache.dll` no longer holds the path of a PDB file or of the folder of the sources, and no PDB file is written next to it; the code is the same.
- **Debug builds:** `ucache_runtests()` and the internal self tests it ran are gone; `ucache_lasterror()` stays.
- **Code cleanup:** `ucache_set()` and `ucache_add()` share one implementation, as do `ucache_inc()` and `ucache_dec()`; code inherited from WinCache that the user cache never used (process-local caches and locks, fixed-address mappings, realloc and strdup in shared memory) is removed, and two small process-local allocations are now freed at shutdown. Scripts see no difference.
- **The sources:** reformatted (braces on the line of their statement, aligned columns), with every comment a `//` comment and a doc comment for every function, which gives its parameters and what it returns; the code is the same.

## 1.0.0.1

PHP 7.3 to 8.5, a scavenger that runs at the end of requests and can evict, values stored without holding the cache lock, and fixes of many bugs that 1.0.0.0 kept from WinCache 2.0.0.8.

- **PHP 7.3, 7.4, 8.0, 8.1, 8.2, 8.3, 8.4 and 8.5,** each with a DLL of its own, next to 7.2. On PHP 8 the optional parameters have their defaults in arginfo, so named arguments work: `ucache_set($values, ttl: 60)`, `ucache_info(key: $key)`.
- **A new scavenger,** built on the scavenger of Datasteam's 2018-2020 fork of WinCache 2.0.0.8 and on its gc settings, `ucache.gc.threshold`, `ucache.gc.interval`, `ucache.gc.step` and `ucache.gc.ttl`, but run at the end of requests rather than by the fork's `wincache_ucache_gc()`, which ucache does not have: once `ucache.gc.interval` seconds (10 by default; 0 turns this off) have passed since the last step in any process of the pool, the next request to end runs a step, which goes through `ucache.gc.step` hash buckets (0, the default, sizes the steps so that they go through the whole table in about 5 minutes while requests keep coming) and stops after about 1 ms under the cache lock. A step removes the expired entries and, with `ucache.gc.ttl`, the entries unused for that many seconds, whatever their ttl; with `ucache.gc.threshold`, writes run steps too while free memory is at or below that percentage of the cache, and the steps at the end of requests run only then. 1.0.0.0 ran a step of 16 buckets inside a write at most every 10 seconds, so a cache that was only read was never scavenged, and it removed an entry once its ttl had passed since its last use instead of since it was stored.
- **A full cache, and expired entries on contact:** a `ucache_set()` or `ucache_add()` that runs out of memory runs a full pass over the table, which removes the expired entries and, with `ucache.gc.evict`, evicts the entries unused for the longest time until that percentage of the cache is free, and then tries again, where 1.0.0.0 failed the write. Every call that looks up a key removes the expired entries it passes, so storing a key again after it expired leaves one entry, where 1.0.0.0 left two, and deleting an expired key removes it. `ucache_info()` reports what the scavenger removed and evicted and when it last ran (`last_scavenge_seconds`, `last_scavenge_count`, `total_scavenged_count` and `total_evicted_count`).
- **Values stored without the cache lock:** `ucache_set()` and `ucache_add()` serialize the objects of a value first and then build its entry in shared memory without holding the cache lock, and `ucache_get()` unserializes objects once it has released it, so `__sleep()`, `__wakeup()`, `__serialize()`, `__unserialize()` and the methods of `Serializable` no longer run under the lock, readers no longer wait while a value is copied in, and the cache functions work inside `Serializable::serialize()` and `Serializable::unserialize()`, where 1.0.0.0 corrupted both the nested value and the enclosing object. A fatal error during a call (memory_limit while `ucache_get()` copies a big value, for example) no longer leaves the cache lock held, which made every other process of the pool wait until the failing one exited. The cost: with several processes writing at once, aggregate `ucache_set()` throughput is about 2 to 2.7 times lower than in 1.0.0.0 with 2 to 6 writers (PHP 7.2), as concurrent copies take turns on the allocator's lock for each allocation; a single writer is as fast.
- **Fixes of bugs that 1.0.0.0 kept from WinCache 2.0.0.8,** among them: reading an array no longer leaks request memory (about 1.2 KB per read); deleting, replacing or scavenging an entry no longer takes time in proportion to the number of entries, and a large entry is freed after the cache lock has been released, in time linear in its size instead of quadratic; a value nested more than 10,000 levels deep is refused instead of crashing the process; a value whose serialization throws (a Closure, for example) is no longer stored as a broken entry; a fatal error during `ucache_set()` no longer loses shared memory until every process of the pool has exited; `ucache_get()` returns false when an object of the value cannot be unserialized, where 1.0.0.0 put null in the object's place; integer keys in the array forms of `ucache_get()`, `ucache_set()` and `ucache_add()`, and large ttls, are no longer cut to 32 bits; `ucache_get()` returns the numeric keys of an array of keys as integer keys; `$success` no longer leaks the value that its variable held; and `$GLOBALS` can be stored.
- **`ucache.prefix`** sets the prefix of the function names, in place of `ucache_`, for code that already defines functions of these names (a wrapper around `wincache_ucache_*()`, for example).
- **Other changes:** `ucache_info()` takes `offset` and `limit`, which list a part of the entries without copying the others; every function checks its arguments first, so invalid arguments throw a `TypeError` or an `ArgumentCountError` (a warning on PHP 7 without `strict_types`) even with the cache off, where 1.0.0.0 returned false silently; `ini_get()` and `phpinfo()` show the whole `ucache.namesalt`, of which only the first 8 characters are used, as before; and `ucache.localheap`, a debugging setting with which no value could be read back, is removed.
- **ucache.php,** the statistics page, in the source code archive, is rewritten: it shows the settings, the memory use, the hit and miss counts, what the scavenger removed and evicted and when it last ran, the entries 250 per page (copying only those) and the value stored under a key; it escapes everything it prints, clears the cache with a token-protected form instead of a link, refuses to be shown in a frame, works on PHP 8 and no longer needs the GD extension. With `USE_AUTHENTICATION` at 0 it now shows the values too, so anyone who can reach it can read the cache, but it still offers no Clear All.

The full list of differences from WinCache 2.0.0.8, whose behaviour 1.0.0.0 kept apart from its three fixes, is in the [README](https://github.com/pkoutsogiannis/ucache/blob/v1.0.0.1/README.md#differences-from-wincache-2008).
- **build-all.bat:** builds and tests `php_ucache.dll` for every PHP version, one after the other, and lists the versions that passed and failed (`build-all.bat install` installs each version whose tests passed).

## 1.0.0.0

The first release, for PHP 7.2 only (WinCache 2.0.0.8's sources do not compile for 7.3 and later). It keeps the API and the behaviour of WinCache's user cache under new names, and fixes three memory-safety bugs.

- **Functions:** `ucache_get()`, `ucache_set()`, `ucache_add()`, `ucache_delete()`, `ucache_clear()`, `ucache_exists()`, `ucache_info()`, `ucache_meminfo()`, `ucache_inc()`, `ucache_dec()` and `ucache_cas()`, in place of `wincache_ucache_*()`, with the same arguments and return values. Debug builds also have `ucache_lasterror()` and `ucache_runtests()`, in place of `wincache_ucache_lasterror()` and `wincache_runtests()`.
- **Settings:** `ucache.enabled` and `ucache.size` (5 to 930 MB, 8 by default) in place of `wincache.ucenabled` and `wincache.ucachesize`, and `ucache.enablecli`, `ucache.namesalt`, `ucache.apppoolid`, `ucache.filemapdir`, `ucache.debuglevel` and `ucache.localheap` (a debugging setting: leave it at 0) in place of the `wincache.*` settings of the same names. As with WinCache, the processes of one IIS application pool, or else those with the same parent process, share a cache; ucache does not see the data that WinCache stores.
- **Left out:** the file cache and the resolve-path cache, with their file change notification (`wincache_fcache_*()`, `wincache_rplist_*()`, `wincache_fcnotify_*()`, `wincache_refresh_if_changed()` and the settings `wincache.fcenabled`, `fcachesize`, `maxfilesize`, `filecount`, `chkinterval`, `ttlmax`, `ignorelist`, `fcenabledfilter` and `fcndetect`), the rerouting of PHP's file functions (`wincache.reroute_enabled`), the session handler (`session.save_handler = wincache`, `wincache.scachesize`, `wincache_scache_*()`), `wincache_lock()` and `wincache_unlock()`, and ETW tracing.
- **The scavenger is WinCache's:** every `ucache_set()`, `ucache_add()`, `ucache_delete()`, `ucache_inc()`, `ucache_dec()` and `ucache_cas()` runs a step at most every 10 seconds, which looks at 16 hash buckets and removes their entries whose ttl has passed since they were last used. Expired entries can no longer be read, but keep their memory until a step removes them; a cache that is only read is never scavenged, and a write that finds the cache full fails. There are no settings for it.
- **Three memory-safety fixes:** `ucache_set()` and `ucache_add()` no longer write their ttl, an 8-byte integer, into a 4-byte variable, which overwrote the stack next to it; `ucache.size` is no longer written as an 8-byte value into a 4-byte field and read back as a 32-bit unsigned number (with WinCache 2.0.0.8, a negative size gave 930 MB and `4G` gave 5 MB): it is read whole, then clamped to 5 to 930 MB; and `ucache_delete()` with an array of keys no longer turns the integer elements of the caller's array into strings in place, which could crash a FastCGI worker running opcache.
- **ucache.php,** the statistics page, in the source code archive: WinCache's `wincache.php` with only its Summary and User Cache pages, which show the settings, the memory use, the hit and miss counts and the entries, and, with authentication on, the value stored under a key and a Clear All link. It refuses to work while its `PASSWORD` is the default, `ucache`, and its charts need the GD extension.
